# 套路推荐对照（放数据进来时用）

> 用途：用户丢进一批数据、问「适合做什么套路」时，**先按本文决策顺序推荐 1 个主套路**（必要时加 1 个备选），再打开对应 `Decisiontree/`。  
> 原则：系统只有 **发病 / 预后** 两块地基；其余都是方法后缀。禁止为新数据新开第三块地基。  
> 决策树总表：`Decisiontree/README.md`。地基说明：`docs/汇报_流水线地基与轨迹案例.md`。

---

## 0. 推荐时必须先看清的 6 件事

从用户数据（列名、表结构、说明）里填这张表，再往下走。缺项就问用户，不要猜结局。

| # | 问题 | 记什么 |
|---|------|--------|
| 1 | **结局** | 二分类发病 / 时间+事件（死亡等） / 竞争事件 / 治疗效应 / 多波次变化 |
| 2 | **暴露** | 一个复合指标 / 很多复合指标批量 / 药物或操作 / 每日轨迹 / 小时级时序 / 环境混合物 / 多波累积 |
| 3 | **库** | 单库 / 双库（发现+验证或平行） / 多库池化 |
| 4 | **时间结构** | 横断面一次测量 / ICU 每日实验室 / 小时级 chart / 队列多波（CHARLS/ELSA/NHANES 周期） |
| 5 | **样本量** | 大致 N、事件数（小样本列线图 / ML 与双库批量不是同一条） |
| 6 | **用户要的产物** | 关联 OR/HR、预测模型、因果（IPW/靶向试验）、轨迹分型、动态预测 |

推荐话术：先说「地基 = 发病或预后」，再说「主套路名 + `run/` 入口 + 决策树文件」，最后用一句话说明为什么不是相邻套路。

## 1. 决策顺序（从上往下，命中即停）

按这个顺序匹配。上面的条比下面的条更「特殊」；不要一看到死亡就一律丢进预后双库。

### A. 数据形态先定死的专项（命中就不要改推荐成普通 logistic/Cox）

| 若数据是这样 | 主套路 | 地基 | 入口 | 决策树 |
|--------------|--------|------|------|--------|
| **小时级**生命体征/实验室长表（chart time），要动态预测院内死亡，并和评分对照 | **两阶段 Transformer（TST）** | 预后预测 | `run/two_stage_transformer_stroke/` | `decision_tree_two_stage_transformer_stroke.md` |
| 只有短序列、单库、轻量 Transformer（非小时→日两阶段） | Transformer AKI 单库 | 预后预测 | `run/transformer_shortseq/` | `decision_tree_transformer_aki_single.md` |
| **入院后每日**同一复合指标的重复测量 + 死亡时间，要潜类别轨迹 | **轨迹预后 JLCM** | 预后 | `run/trajectory_prognosis/` | `decision_tree_trajectory_prognosis_apri.md` |
| 纵向重复测量，但结局是**发病**（类别后再 logistic），不是死亡分层 | 轨迹发病 | 发病 | `run/trajectory_incidence/` | `decision_tree_trajectory_incidence_aki.md` |
| **主事件 vs 竞争事件**（如 AKI vs 死亡/出院），需要 CIF / Fine–Gray | **竞争风险** | 预后 | `run/competing_risk/` | `decision_tree_competing_risk_stroke.md` |
| 暴露是**治疗/药物/操作**（不是复合指标），要平衡后比较结局 | **IPW** | 发病或预后（看结局） | `run/ipw_diabetes_stroke/` 或 `run/ipw_pe_alteplase/` | `decision_tree_ipw_diabetes_stroke.md` |
| 明确的**靶向试验**模拟（资格、时间零点、治疗策略） | 靶向试验 | 预后/因果 | `run/target_trial/` | `decision_tree_target_trial_rasi_aki.md` |
| **≥2 个波次**的同一指标，要交叉滞后 / 双向关联 | 交叉滞后 | 发病纵向 | `run/cross_lagged/` | `decision_tree_cross_lagged_frailty.md`（或 suicide 树） |
| **多波累积暴露**（如两波算 cum）+ k-means 分型 + 新发结局 | 累积暴露 × k-means | 发病 | `run/cum_egdr_kmeans_ckm/` | `decision_tree_cum_egdr_kmeans_ckm.md` |
| 多种**环境暴露混合物**（VOC 等）+ NHANES 权重，要 WQS/BKMR/qgcomp | 环境暴露 | 发病（加权） | `run/environment/` | `decision_tree_environment_voc_batch.md` |
| 多个 ICU 库要**池化**成一个队列再建模（不是两库平行外验） | 数据库池化 | 预后 | `run/database_pooling/` | `decision_tree_database_pooling.md` |
| 同一批人：**先发病（是否发生）再在病例里做预后** | SLE–AKI 两阶段 | 发病 → 预后 | `run/sle_aki_inc_prog/` | `decision_tree_sle_aki_inc_prog.md` |
| 临床小样本、要**列线图**（成功/失败二分类，N 通常数百） | 列线图 | 发病 | `run/gallstone_nomogram/` | `decision_tree_gallstone_nomogram.md` |
| 小 N 机器学习（单指标或全指标，要 bootstrap CI） | 小样本 ML | 发病或预后 | 模板 `config_ml_small_sample` | 见 `.cursor/skills/ml-small-sample/SKILL.md` |

### B. 没命中 A 时：默认走两块地基批量

| 若数据是这样 | 主套路 | 入口 | 决策树 |
|--------------|--------|------|--------|
| 横断面或基线一次测量；结局是**会不会发生**（0/1）；**两个库**可对齐列名；暴露是复合指标 | **发病双库批量** | `run/incidence/run_incidence_dual_batch.R` | `decision_tree_incidence_dual_batch.md` |
| 同上，但**只有一个库** | 单库发病 | `run/incidence/run_incidence_single.R` | `decision_tree_incidence_single.md` |
| 有 `futime` + 事件（死亡等）；**两个库**；暴露是基线复合指标；要 HR / KM | **预后双库批量** | `run/survival/run_survival_dual_batch.R` | `decision_tree_survival_dual_batch.md` |
| 同上，用户明确要**预测模型**（多算法、ROC、SHAP），而不只是 Cox 关联表 | **ML 双库** | `run/ml/run_ml_dual_batch.R` | `decision_tree_ml_dual_batch.md` |
| ML 且是「一库全做开发、另一库全做外部验证」 | ML 外部验证 | 研究目录 `run_ml_external_validation.R` | `decision_tree_ml_dual_batch.md`（外验段）+ `decision_tree_ml_dual_prognosis_aki_dev_ext.md` |

NHANES 加权发病：仍走发病地基，用 `config_incidence_nhanes*.template.R`（加权 logistic / 加权亚组），不要改推荐成环境混合物套路，除非暴露是多种污染物。

## 2. 相邻套路怎么拆开（最容易推错）

| 用户数据看起来像 | 推荐 | 不要推荐成 |
|------------------|------|------------|
| 有死亡，但是**基线一次**抽血/复合指标 | 预后双库（关联）或 ML（若要预测） | 轨迹预后、TST |
| 有死亡，且**每天一条**实验室 | 轨迹预后 | 预后双库、TST |
| 有死亡，且**每小时** chart | TST | 轨迹预后 |
| 死亡和另一种事件抢人（出院、竞争病） | 竞争风险 | 普通 Cox 预后双库 |
| 分组是**吃没吃药 / 做没做操作** | IPW | 把药物当复合指标丢进发病 batch |
| 两个库都有，但是要**合成一个训练集** | 数据库池化 | 发病/预后双库（双库是平行分析或开发–验证） |
| 两个库，开发与验证**分开** | 预后/发病双库，或 ML 外验 | 池化 |
| 多波次「指标变了再预测新发病」 | 交叉滞后或累积 k-means | 单次横断面发病 |
| 只要 OR/HR 表、RCS、亚组、中介 | 发病或预后双库 | ML、TST |
| 要和 SOFA/APSIII 比 AUC、要网页计算器 | ML 或 TST（看是不是时序） | 只跑 Cox 关联 |

## 3. 地基一句话

| 用户说法 | 地基 |
|----------|------|
| 发病、患病、OR、病例对照、新发 | **发病** |
| 死亡、存活时间、HR、KM、28 天 | **预后** |
| IPW + 死亡 | **预后** + IPW |
| IPW + 是否发病 | **发病** + IPW |
| 轨迹再预测死亡 | **预后** + 轨迹 |
| 轨迹后再看是否发病 | **发病** + 轨迹 |
| 竞争风险 | **预后** + competing |
| 小时级动态预测死亡 | **预后** + TST |

## 5. 推荐之后不要立刻开跑

选定套路后，写 config 前仍要过门控（见 pipeline-foundation）：

1. 列名能否双库对齐（双库课题）
2. 逐列审阅，疾病变量不进协变量
3. 暴露是否复合指标真公式（IPW/药物暴露、环境混合物除外）
4. 分层、年龄切点是否两库都能算
5. 用户确认决策树后再 `--shared-only`

数据对不上某套路的硬条件时（例如无小时级长表却要 TST、无竞争事件却要 Fine–Gray、无多波却要交叉滞后），**改推下一档默认套路**，并写明缺什么。
